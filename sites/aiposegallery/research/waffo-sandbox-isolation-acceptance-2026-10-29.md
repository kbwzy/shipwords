# Waffo 沙箱隔离与验收方案（2026-10-29）

状态：**Waffo 自动计费已在代码中关闭；真实沙箱交易、平台回调和退款均未验收**。checkout 返回 503，所有已验签的 Waffo 事件返回 500 且不记为处理完成，Waffo 账本写入也会失败。现有资料记录 test webhook 指向生产域名；交易前必须重新核实，不能以本文件或 checkout session 创建成功作为隔离证明。正式价格、权益未确定；测试商品价格不代表正式价格。

## 现在可执行：离线验收

在仓库根目录执行 `pnpm --filter @shipwords/core check` 和 `pnpm --filter @shipwords/jobs check`。测试使用 workerd 内存 D1，不连接支付平台；签名测试使用临时生成的密钥。检查关闭状态、签名和模式校验、退款事件重试、首次退款快照不可发放、跨 provider 归属，以及 Waffo 凭据禁用 mock。它不能证明 Waffo 的真实字段、签名、公钥、投递或退款行为。

## 接入真实沙箱前的硬门槛

以下是后续实施清单；当前任务未授权修改配置、部署、后台或支付，均未执行。任何一项证据缺失时停止：

1. 独立环境：单独的沙箱应用和独立空 D1，独立域名、路由、账户/凭据、日志与必要的存储；逐项核对资源绑定及数据库 ID，与生产不同。禁止使用共享生产 D1/R2 的普通 preview 作为隔离环境。隔离环境只配置 test 凭据、test store 和 test-only 商品。不得复制真实用户数据，不记录密钥或 checkout token。
2. test webhook：在 Waffo test 模式核对**所有**启用的 HTTP webhook 与订阅，确认生产域名不再接收任何测试事件，且目标仅为独立沙箱的 `/api/webhooks/waffo`。需要变更时仅修改 test 模式设置，并由负责人员记录变更前后脱敏证据；不动 production webhook。确认无需生产域名接收或转发事件。当前已知指向生产，因此此门槛未通过。
3. 主机保护：当前 checkout 已关闭；test 模式 webhook 请求 URL 仅允许 `localhost`、回环地址、`.localhost`、`.test`，或首段为 `test` / `sandbox` 的主机名。使用单独沙箱主机，例如 `sandbox.<专用域名>`；必须另行核实它实际绑定的资源，因为名称检查不证明隔离。避免在代理中把外部沙箱请求改写成生产 URL。生产或 test 配置不得共用密钥或通用 webhook 公钥覆盖值。
4. 明确 test 环境变量、store ID 和平台 test 公钥来源；确认凭据确属测试模式、事件 `mode=test` 且 `storeId` 符合配置。由于现有 server 对未识别环境值回落到 test，不能把错误配置视为安全保证；必须由部署负责人核实实际运行配置。验收需确认平台是否要求公网 HTTPS，以及签名验证所用 SDK 的实际运行时兼容性。
5. 核对测试商品 ID、平台币种与总金额、测试站点服务端产品额度和预期值一致；仅供沙箱。准备测试用户和订单，确认余额为零。禁止使用真实卡、真实付款或未经确认的支付手段；在确认隔离、平台官方测试方式及测试授权前，停止于此。

## 隔离条件满足后的验收步骤

以下是待实现安全对账并通过独立审查后的验收目标，**当前关闭状态无法执行成功交易或退款验收**。届时需由获授权的负责人在隔离环境执行；任何失败或回调流向不明立即停止。只记录脱敏订单/事件引用、时间、结果，不保存 checkout URL、签名、个人信息或凭据。

1. 创建一次 test checkout，确认订单为 pending，平台 test 商品、币种、金额和返回地址正确；不输入真实支付资料。若平台确认提供不产生真实资金流的测试方式，另行按授权执行模拟支付。查询平台 API，记录支付状态、订单引用、金额和币种；核对数据库的订单归属和支付记录。仅在平台确认 succeeded 后期待发放一次测试额度。
2. 核对沙箱服务收到真实 test 签名回调且完成验签和 API 复查；重复投递同一事件、不同事件指向同一支付，以及同一订单的不同支付尝试，余额均不得重复增加。核对生产无测试请求或写入的证据。不同支付确实成功时须人工调查额外收费，系统不会把第二笔当成第二份权益。
3. 模拟 API 短暂失败或状态尚未同步，验证非 2xx、事件未标记完成，恢复后重试最终收敛。验证错签名、错误模式/店铺、未知订单、欠付和币种错误不发额度；验证日志不含秘密。
4. 仅在平台明确支持无真实资金流的测试退款且获得授权后，验证部分、全额、重复和乱序通知。以平台查询快照为准，检查 ledger、lot、余额和欠款；验证已消费额度的退款。失败退款不扣额度。留存每步前后的脱敏记录及一致性结果。
5. 测试完成后检查沙箱测试回调和资源，按负责人的测试环境生命周期处理。上线前须独立复核 Waffo API 真实字段、退款分页/一致性、产品价格权益、业务审核和生产安全配置；本文件不构成上线批准。

## 已知实现边界

- 本地 SDK 0.26.0 的 `docs/webhook-guide.md` 区分 `chargedAmount`、`refundedAmount`、`originalChargedAmount` 与 `listPrice`，且渠道金额可能缺失；`docs/graphql-guide.md` 提供按可选 `refundTicketMerchantExternalId` 查询退款及 `pspAmountDetails` 的示例，但未证明该标识总存在、与特定 payment 的完整绑定、退款列表完整性及渠道实收的可查询字段。因此不使用标价计算发放或退款比例；不得从签名事件直接发额度。
- 有签名的事件保存到内部触发对象的订单、支付和退款工单标识均为可选；目前并不查询或确认任何退款。无论标识有无，handler 返回 500、不写入已处理事件。平台重试可能过期；需告警及人工恢复机制，不能把失败重试当作永久队列。
- 同订单多笔成功支付及对原支付的退款仍需按支付和退款唯一标识逐笔对账，当前全部阻塞，不能判定成功。旧版账本键的迁移、并发和重复事件也需在恢复前独立验证。
- 共享账本对首次观察到已退款或争议的支付，将发放与初始扣回、余额和支付状态写入同一 D1 批次；批次内核对退款与争议快照，发生并发变化时重新计算。该路径有本地自动化测试，不能替代真实支付平台验收。
- 项目规则要求合并前独立审查；恢复 Waffo 前还须核实币种精度、退款分页/一致性、真实环境配置及数据迁移。
