# Pose private-file deletion and retention (local design; not enabled)

## Explicit deletion

`deletePoseTask` is a server primitive, not a registered endpoint. It verifies the signed, unexpired guest cookie and the configured exact Origin, uses the task ID only to find an owner-matching D1 row, and handles only `succeeded` or `failed` tasks. Missing, forged or expired identity cannot authorize deletion. Unknown and pending states are not terminal. Its 200 response means only that the known task keys and the D1-referenced output were checked absent in this bucket while a write barrier was held. It does not cover unreferenced result objects, other providers, logs, caches, backups, or copies downloaded by users.

The admission row is deliberately retained without changes, including its owner, request key, digest, day, status, and output key. The current UTC-day site and owner limits count these rows, including failed and deleted tasks; deleting them would reopen paid capacity and break idempotency. This implementation does not define or implement later D1 retention or full erasure. An output key may consequently refer to an absent object. Any future D1 cleanup policy must separately preserve limits and idempotency for their full required periods.

## Required integration before enabling

- Implement a **durable task write barrier** and pass it as `PoseCleanupBarrier`. `sealAndRun` must permanently seal the exact task before draining all in-flight writes, serialize deletion attempts, and keep the seal across crashes, retries and instance restarts. The callback must run only after the seal and drain are confirmed. A local mutex, a terminal-state read, a boolean provided by a browser, or a workflow status check alone does not meet this contract.
- All task writers must participate in that same barrier **before any side effect**, including initial input storage and replay, workflow preparation, quote/manifest and result writes, retries, recovery, manual operator actions and any future writer. Existing writers do not participate. The seal must prevent a previously admitted request or queued workflow from writing after deletion; it must also prevent re-creation after the callback. Validate these properties under concurrent requests, crashes and retries in the actual deployed coordination system. This repository does not currently supply such a barrier; without it the helper returns 503 and must not be exposed as working deletion.
- Wire a same-origin POST route with a server-configured canonical origin, secret, D1 and private R2 binding. The ID can be supplied by the client, but never accept an owner, key, bucket or barrier from it. Preserve the no-store response and avoid logging cookies, prompts, URLs or object contents. Return and present 409/503 accurately; R2/D1 are not one transaction and a 503 may mean partial deletion. Retry is safe only while the durable seal remains enforced. Unknown keys, metadata mismatch, shared output references, R2 failures, or verification failures require investigation rather than a success claim.
- The existing guest cookie expires after 24 hours and cannot authorize deletion thereafter. A separate, verified recovery/authentication mechanism or clearly bounded access policy is needed for later deletion; do not accept an owner ID as a substitute.
- Check the data-processing agreement and separately implement/verify deletion or retention for upstream provider uploads and outputs, delivery caches, backups and logs. No assertion about their deletion is made here.

## Bucket lifecycle for orphans and retention

Concurrent result transfers can create random `pose-media/` objects that are never referenced by D1 or the winning manifest. They cannot be safely discovered per task from existing metadata. Configure Cloudflare R2 **bucket** lifecycle expiration for both `pose-tasks/` and `pose-media/` prefixes, after choosing and approving a retention duration and verifying the dedicated bucket and all prefix users. This expires referenced objects as well as orphans: the current layout cannot expire only orphan outputs. Ensure the chosen duration exceeds the maximum active workflow, recovery and advertised access periods; coordinate expiration with product behavior so missing inputs/results are handled safely. If a task can run indefinitely, a fixed expiry alone cannot guarantee its inputs survive.

No duration, bucket, account, or rule is assumed or configured by this document. Before any future change, inspect and preserve existing lifecycle rules and bucket locks; do not replace unrelated rules. Confirm the configured rules on the actual bucket and test expiry with disposable objects. R2 expiration is asynchronous, usually within 24 hours after the expiration time, and lock rules can delay deletion; it is not an immediate or exact deletion guarantee. See [R2 object lifecycles](https://developers.cloudflare.com/r2/buckets/object-lifecycles/) and [R2 bucket locks](https://developers.cloudflare.com/r2/buckets/bucket-locks/). These local workerd tests do not verify real lifecycle scheduling, production bucket locks, or provider retention.
